# Stage 0 findings — OpenCode 1.18.30 durable log and live server

Date: 2026-09-10. Sources:
- A read-only census (`scripts/census.mts`) over one real user's
  `opencode.db`: 1.9 GB, 505 sessions, 50 of them with an event log.
- Sandboxed live recordings (`scripts/probe-live.mts`) of the real
  `opencode` 1.18.30 TUI, launched with `--hostname 127.0.0.1 --port <free>`
  and a per-spawn password, using the free `opencode/big-pickle` model in a
  throwaway HOME/XDG tree.

Fixtures: `testing/fixtures/durable/*.json` (sanitised census extractions),
`testing/fixtures/live/*.json` (probe recordings) and
`testing/fixtures/schema.sql` (the real DDL of the five tables the reader uses).

This document is the evidence the reader's rules are argued from. When a later
OpenCode release changes a finding, re-run both scripts and update it; do not
patch the reader around a stale assumption.

## Durable log (census)

| # | Hypothesis | Result | Consequence |
|---|---|---|---|
| 1 | `event.seq` is gapless per aggregate, starting at 0 | **Holds** (50/50) | A `seq > cursor` tail never skips rows |
| 2 | A user message's parts are written before the first assistant answering it | **Holds for prompts.** 4/50 sessions rewrite a `compaction` part on the synthetic compaction user message 7–11 events after its summary assistant starts | Commit a user message when the first assistant with `parentID === user.id` appears. Later rewrites are ignored (see 9) |
| 3 | Nothing changes an assistant message after the write that sets `time.completed` | **Holds** (0 part updates, 0 message updates, across 6,684 assistant messages) | Completion is final: commit once, read content from the projection at that moment |
| 4 | Which `finish` ends a user turn | Final assistant per user turn: `stop` 264, **`tool-calls` 139**, none 47 (the none cases are aborts and API errors: `MessageAbortedError` 36, `APIError` 10). `stop` never appears mid-turn | **The durable log cannot tell when a turn ended.** Turn boundaries come only from the live `session.status` |
| 5 | `message.removed` contexts | 14 removals: 7 incomplete user messages, 7 completed assistants (revert/undo) | Removal is not propagated; consumers keep the entry until they re-read history, which comes from the projection and is already correct. This matches the structured runtime |
| 6 | Child (`task`) sessions have their own aggregate | **Holds**: 0 foreign-session events in any aggregate; 14 child sessions, each with its own log | Tailing our aggregate is the session filter; descendant sessions need an explicit lookup (`session.parent_id`) |
| 7 | Last-write-wins replay of the log equals the `message`/`part` projection | **Holds**: 7,182/7,182 messages, 29,355/29,356 parts. The single mismatch is a part rewritten between the census's event read and its table read in a session active during the census | The projection is an independent oracle for the assembler. The reader must read cursor and projection in **one transaction** (the mismatch is exactly the race that rule prevents) |
| 8 | `message.data` / `part.data` omit their ids | **Holds** (0 of 7,216 message rows and 29,263 part rows carry `id`/`sessionID`/`messageID`) | Assembly adds ids from columns: `info = { ...data, id, sessionID }`, parts `{ ...data, id, messageID, sessionID }` |
| 9 | User messages are rewritten after commit | 6,962 rewrites. Only `summary` ever changes (516 times); every other rewrite is identical | Ignoring post-commit user rewrites loses only `summary.diffs`, which nothing renders |

Other shape facts:
- **Event types:** `message.part.updated.1` 70,617, `message.updated.1` 27,447, `session.updated.1` 7,513, `session.created.1` 32, `message.removed.1` 14. Every type is version 1.
- **Part types:** tool 42,467, reasoning 9,749, step-start 6,671, step-finish 6,641, text 4,996, patch 82, compaction 10, file 1.
- **Updates per assistant message:** usually 3 (created, finish set, completed; the live run shows `finish: "stop"` is written one event **before** `time.completed`).
- **Import-seeded logs:** sessions seeded by `opencode import` (Agent Code's terminal sessions and switch targets) start their log at `session.updated.1`. Imported messages never appear in the log (55 messages in 5 sessions), so **history must come from the projection**, never from replaying the log.
- **Queued prompts** occur in 16/50 sessions.

## Live server (probe, OpenCode 1.18.30)

| Question | Answer |
|---|---|
| Does TUI `--hostname/--port` expose a real server? | Yes. It answers about 3.5–9 s after spawn (first TUI paint at a similar time). Requests block while the project instance boots, so the durable reader must not wait on the live channel |
| Is auth enforced with `OPENCODE_SERVER_PASSWORD`? | Yes. No credentials: `401`. `Authorization: Basic base64(opencode:<password>)`: `200`. The TUI itself keeps working (it sends the same credentials) |
| Does the durable row precede the bus event? | Yes, for every recorded event, so a live event is a valid doorbell for a synchronous durable read |
| `session.status` | `{ sessionID, status: { type: 'busy' \| 'idle' } }`. `busy` repeats 2–5× within one turn (per step); the turn ends with `status idle`, and a `session.idle { sessionID }` in the same tick |
| Permission request | `permission.asked { id: 'per_…', sessionID, permission, patterns[], metadata, always[], tool: { messageID, callID } }`, then `permission.replied { sessionID, requestID, reply }`. `session.status` stays `busy` while waiting |
| Question request | `question.asked { id: 'que_…', sessionID, questions: [{ question, header, options[] }], … }`, then `question.rejected { sessionID, requestID }` (or `question.replied`) |
| Re-sync endpoints | `GET /session/status` returns `{ [sessionID]: { type } }` for non-idle sessions only (`{}` when idle). `GET /permission` and `GET /question` return the pending requests in the event's shape |
| Answer endpoints | `POST /permission/:id/reply { reply: 'once'\|'always'\|'reject' }` → `200 true`. `POST /question/:id/reject` → `200 true` |
| Queued prompt | The second prompt runs inside the same busy span: busy ×5, one idle at the end. **One live turn can hold several user messages** |
| Noise | Startup: `plugin.added` ×90, `catalog.updated`, `integration.updated`, `reference.updated`. Per turn: `session.diff`, `message.part.delta`, `file.*`. None affect committed state or status |
| Port already bound | `testing/fixtures/live/port-conflict.json`: the TUI neither exits nor paints (0 PTY bytes after 25 s), and the port stays with the other listener. The pane would look blank and hung. The allocate→spawn race is tiny, but the live channel needs a connect deadline and a visible `server-unreachable` diagnostic, and the durable channel must not depend on the live one |
| Project snapshot hazard | A project directory inside a large git worktree makes the server accept connections and answer nothing while the instance snapshots the worktree (first probe run: 300 s). This is host-environment behavior, not a reader bug, but it means live requests need timeouts |

## Unknowns closed and still open

Closed:
- Bus names and payloads
- `--port` plus password behavior
- Re-sync endpoints
- Queued-prompt sequence
- Durable ordering invariants 1–9
- Durable-before-bus ordering
- Compaction shape: a rewritten `compaction` part on the synthetic user message

Still open (tracked in the Agent Code decomposition):
- Whether a child session's permission request reaches the parent TUI's bus. The probe's free model never delegated to a `task` subagent. The live reader keeps requests for descendant sessions (known from `session.parent_id`/`session.created`) so the behavior is correct either way.
- `SQLITE_BUSY` frequency for a reader beside a live writer. None was observed in the probe's 20 ms tail.
